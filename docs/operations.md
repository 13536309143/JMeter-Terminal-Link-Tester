# 运行维护与故障排查

## 日常执行

运行前确认配置和目标服务；用小负载检查契约，再增加终端数或减少间隔。先保存基线结果。每次记录机器、操作系统、Java/JMeter/插件版本、目标软件版本、QoS、消息大小和采集阶段。

不要在图形界面进行正式大负载。JMeter GUI 的结果树会增加资源开销；正式运行使用 CLI。`resources.csv` 仅代表负载机及 JMeter 进程，目标 Broker、数据库和网络需单独监控。

## 排查顺序

| 现象 | 检查项 |
| --- | --- |
| doctor 失败 | Java 路径、JMeter 清单版本、插件缺失或摘要不符 |
| 连接失败 | 目标地址/端口、监听状态、认证、网络策略；当前配置不支持 TLS |
| MQTT 发布成功但完整率低 | 采集订阅阶段、Topic/ACL、非法消息、队列溢出、独立采集器日志 |
| TCP 请求超时 | 服务端 LF 分帧、响应超时、消息 ID、连接重用和服务端连接队列 |
| UDP 超时或少包 | 对端端口、响应关联 ID、接收窗口、数据报大小、丢失和乱序记录 |
| HTTP 失败 | 方法、路径、期望状态码、Content-Type、Bearer 环境变量、响应 JSON 契约 |
| P95 偏高 | 目标负载、网络、服务端处理、采集队列、负载机 CPU/内存；不要把上报间隔当作网络耗时 |
| JMeter 进程正常但门禁失败 | 查看 summary 的每个 gate；进程成功不等于业务校验成功 |

先看 `summary.json`，再核对 `console.log`、`jmeter.log`、`samples.jtl` 与 `collected.jsonl`。MQTT 插件可能在主动断开后记录 EOF 提示，应结合原始采样与采集结论判断，不能仅按日志中某个单词定性。

## 结果保存与升级

按运行目录整体归档，不要只保存截图。备份场景、JMX、CSV、JTL、采集记录、provenance 与 summary；需要完整原生仪表盘时连同 dashboard 归档。升级前保留上一版本程序和配置，运行结果保存到独立目录。

源码环境用固定依赖与摘要部署。便携包完整解压后替换应用目录，不能只替换主可执行文件；Java 与 `_internal` 也属于该版本运行环境。运行包的 `.sha256` 用于核对下载产物。

## 现场验收建议

功能验证先覆盖四协议正常与异常路径，再验证真实采集入库后的回执。容量测试逐级增加负载，保持每级稳态时间足够，记录实际活跃终端与目标资源。长稳验证根据现场计划执行，保存连续监控和故障记录。网络中断、认证拒绝、服务重启和故障恢复需在专用环境单独验证。

本次本地实验是功能与检测链路验证，不提供现场容量上限、72 小时稳定性、可用性或安全测评结论。
